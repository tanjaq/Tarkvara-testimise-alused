Session Plan — 6 Sessions

For groups that meet every other week · manual testing only · 5 homework assignments
The same course and the same slides as the full 13-lesson track — delivered in six sessions instead of thirteen. Each session below names the decks to open, which slides to cover in the time available, and which to leave as reading. Nothing here is a separate copy: every link goes to the same lesson deck, so anything you edit in a lesson shows up here too.
The six sessions
Session 1

Quality Mindset & Why We Test

Decks: Lesson 1 — Testing Fundamentals (all of it) · Lesson 2 — The Purpose of Testing (selected)

Cover in class

  • Lesson 1 in full — intro, AI ground rules, quality, what can be tested
  • Why test — real failures and when software kills
  • The cost of a defect grows with time
  • The goals of software testing

Reading / skip if short

  • Testing happens everywhere and app store reviews
  • Public-sector failures
  • Consequences of defects — the failure slides already make the point
In class: Let's meet, then group work — anatomy of a failure (15 min, groups of 3–4, 2-minute summaries)
No homework. Ask them to come back with one piece of software they consider high quality and one they don't — the closing slide.
Session 2

The Testing Process

Decks: Lesson 3 — The Testing Process

Cover in class

  • SDLC, then waterfall, V-model, agile
  • The ISTQB five-step process and all five steps
  • The seven principles, both halves

Reading / skip if short

  • DevOps lifecycle — useful context, not examinable here
  • The detail slides of steps 2–5 can be summarised from the overview if time runs out
In class: the trip planner combination count (5 min, lands principle 2 hard), then the calculator worksheet in groups
Homework 1: Test process worksheet — calculator. Word version or fill in on the page.
Session 3

Requirements & Architecture

Decks: Lesson 4 — Software Requirements (most of it) · Lesson 5 — Software Architecture (selected)

Cover in class

  • The chain: business need → requirement → test case
  • Requirements are not user stories and good vs bad examples
  • Writing NFRs that can be tested and SMART
  • The SRS document — they need this for the project
  • Architecture: what it is, monolith, layered, microservices, how to choose

Reading / skip if short

  • The two NFR category tables — point at them, don't read them out
  • Event-driven, serverless and modular / monorepo — set as reading
In class: draw your project's architecture in teams and present it
Homework 2: Requirements for your project and project architecture — both into the same SRS document, submitted together.
Session 4

Test Techniques — Static, Black Box, White Box

Decks: Lesson 6 — Static · Lesson 7 — Black Box · Lesson 8 — White Box (all selected)

Cover in class

  • The map of testing techniques — the frame for the whole session
  • Which defect is easier to fix? and peer review
  • Review size decides review quality and PR review etiquette
  • Equivalence partitioning and boundary value analysis — the core of the session
  • Decision tables and state transition testing
  • Three levels of code coverage and what coverage does not tell you

Reading / skip if short

  • Walkthroughs and inspections and static code analysis detail
  • Testing types and use-case testing
  • Coverage example 2 (the loop) — one worked example is enough live
In class: EP and BVA on the trip planner form — the fastest way to make the techniques real. The photo-ordering decision table can start in class and finish as homework.
Homework 3: Decision table + EP/BVA on the trip planner form.
Session 5

Defects & Exploratory Testing

Decks: Lesson 9 — Defect Management & Exploratory Testing

Cover in class

  • Error, defect, failure
  • What exploratory testing actually is and session-based test management
  • Tours and heuristics
  • Bug report fields, evidence from the browser, a complete example
  • Severity is not priority and the bug lifecycle

Reading / skip if short

  • When to explore and what to write down
  • Defects that reach production
  • Root cause analysis — worth 3 minutes if you have them
In class: write a charter and run a 20-minute exploratory session on an app they use, then compare findings
Homework 4: Exploratory session + bug report, filed as a GitHub issue in the Bug-Reporting repo.
Session 6

Test Cases, Test Plan & Documentation

Decks: Lesson 10 — Test Cases & Documentation · one slide from Lesson 3

Cover in class

  • From user story to test case and components of a test case
  • A test case in practice — the worked example that links to the bug report
  • Planning and control from Lesson 3 — the grounding for the test plan they now have to write
  • Confirmation testing and regression testing
  • Best practices for writing test cases

Reading / skip if short

  • The real test case document screenshot
  • Why test cases matter
  • Test management tools — name two, move on
In class: each team drafts the scope and exit criteria of their test plan, out loud, and the others say whether the exit criteria are checkable
Homework 5: Test plan and test cases for your project — SRS sections 7.1 and 7.2. This closes the group project.

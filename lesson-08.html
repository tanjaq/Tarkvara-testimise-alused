Topic 1

Two Kinds of Coverage

Black box → test coverageHow much of the requirements is covered. Did we test everything we promised to build?
White box → code coverageHow much of the code is executed. Did any test ever run this line?

Both numbers can be high while the product is still broken — and one being high tells you nothing about the other.

Topic 2

Three Levels of Code Coverage

Function coverageWas every function in the application called at least once?
Statement coverageWas every line of code executed at least once?
Branch coverageWas every branch — every true and false path — taken?

Each level is stricter than the one before it. 100% branch coverage implies 100% statement coverage; the reverse is not true.

Topic 3

Reading Code as a Graph

Requirement: members get 10% off. Non-members pay the full price.

function finalPrice(price, isMember) {
  let discount;
  if (isMember) {
    discount = 0.1;
  }
  return price - price * discount;
}
Control flow graphBoxes = statements · diamonds = decisions · arrows = possible flow. Statement coverage visits every box; branch coverage walks every arrow out of a diamond.
Topic 4

Example 1 — a Conditional

function calc(a, b) {
  let c = 0;
  if (a > b) {
    c = a;
  }
  return c;
}
Function coveragecalc(1, 1)
The function ran — 100%.
Statement coveragecalc(2, 1)
Every line executed, including c = a.
Branch coveragecalc(2, 1) and calc(1, 3)
Both the true and the false path of the if.

Note that calc(1, 1) gives 100% function coverage while never executing the body of the if. This is why the metric you quote matters.

Example 2 — a Loop

function loop(a) {
  let c = 0;
  for (let i = 0; i < a; i++) {
    c = c + 1;
  }
  return c;
}
Coverage· Function: loop(1)
· Statement: loop(1)
· Branch: loop(2) and loop(0) — the loop body must both run and not run.
Tests coverage will never suggest· loop(-5)

· loop("abs")
· loop(300000000000)
These come from black-box thinking, not from the coverage report.

Example 3 — 100% Statements, Still a Bug

The finalPrice function from the graph, with one test:

test('member gets 10% off', () => {
  expect(finalPrice(100, true)).toBe(90);

Every line ran. Green. Ship it?
Branch coverage: 50%The FALSE arrow out of isMember? was never walked. Branch coverage forces a second test: finalPrice(100, false), expected 100.
Actual result: NaNFor non-members discount stays undefined. The bug lives on the arrow you can't see in the code — the missing else.

Topic 4

Example 5 — Two Decisions, Four Paths

Standard delivery 5 €. Orders of 50 € or more get free standard delivery. Express delivery always costs 12 €.

function deliveryFee(total, isExpress) {
  let fee = 5;
  if (isExpress) {
    fee = 12;
  }
  if (total >= 50) {
    fee = 0;
  }
  return fee;
}

Two decisions in a row → 2 × 2 = 4 paths through the graph. Branch coverage only needs 2 of them.

A + B = 100% branch coverageEach if was TRUE once and FALSE once. The coverage report is fully green.
Path D: free delivery wipes out expressThe second if overwrites the first. Bugs love the combination of decisions — that's what path coverage targets.

Compound Conditions — the One-Character Bug

Requirement: you can rent a car if you are at least 21 and have a licence. The developer typed || instead of &&:

if (age >= 21 || hasLicense) {   // should be &&
  return true;
}
return false;
TestExpected (&&)Actual (||)Branch-coverage testsEach-condition tests
(25, true)truetruePASSPASS

Two tests give 100% statement and branch coverage — and miss the bug. Fix: show that each condition on its own can flip the result. This is called MC/DC and is required for flight-critical aviation software.

Topic 5 · Going further

How Many Tests? Cyclomatic Complexity

Why not test every path?2 ifs → 4 paths
10 ifs → 1 024 paths
1 loop → potentially endless paths

Full path coverage is only realistic for small, critical functions.
McCabe's rule of thumbM = decisions + 1
Count every if, loop, case, &&, ||, ?:.

M = the number of independent paths — a good minimum number of tests.
FunctionDecisionsMAll paths
finalPrice1 if22
canRent1 if + 1 &&33
deliveryFee2 if34

M above ~10 means the function is hard to test — refactor it. Static analysis (Lesson 6) can enforce this: ESLint "complexity": ["warn", 10].

Topic 7

What Coverage Does Not Tell You

  • 100% code coverage does not mean a 100% tested product.
  • Coverage only measures the behaviour of the code that exists.
  • Missing code — a requirement nobody implemented — will never show up in a coverage report.
  • A test that executes a line without asserting anything still counts towards coverage.
Recommendation: black box + white box together give higher test coverage and higher code coverage. Neither replaces the other.
Warm-Up Exercise

Parking Fee — Count Before You Test

2 € per hour; 0 hours costs nothing. Residents who park more than 3 hours get 50% off.

function parkingFee(hours, isResident) {
  if (hours <= 0) {
    return 0;
  }
  let fee = hours * 2;
  if (isResident && hours > 3) {
    fee = fee / 2;
  }
  return fee;
}
  1. Draw the control flow graph
  2. Minimum tests for 100% statement coverage?
  3. Minimum tests for 100% branch coverage?
  4. Which black-box technique adds one more test here?
  5. Going further: cyclomatic complexity? Which test proves hours > 3 matters on its own?
